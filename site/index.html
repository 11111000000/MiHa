01Small, measured — not promised

Most agent frameworks quote a "lightweight core" and then require a runtime, a state store and a schema library. MiHa's budget is a law, enforced by the build: the whole thing — harness, provider adapter, peer exchange, interface layer — is measured every time the gate runs, and the build fails if it does not fit.

02How it works

An application embeds MiHa and gets an agent loop. The model decides; the harness dispatches the tools the application registered; the application's interface renders what happened. Everything that happens is one journal — an append-only log of durable events — and everything reads from it: the model's context, the trace, the session, and what a peer is handed.

the journal — one append-only log of durable events. The entries are the trace, the session and the peer's view of a delegated task — there is no second format.
the projection — the model's context, folded forward one entry at a time. Compaction is a fold, not a special case: what does not fit the budget is collapsed into a digest, and the journal keeps the whole history.
the core — a pure transition function. No I/O, no clock, no storage, no policy. It validates the arguments against its own dialect, plans the tool groups, and emits intents.
the driver — the only effectful part. It performs the intents: calls the provider through the host's request seam, asks the host's approval before each tool runs, races the cancellation, and feeds every result back.
the host surface — seven hooks, and nothing else: the provider, the tools, the approval, the request seam, the journal, the capabilities, the peer. The host owns everything privileged.

03The laws

Every law states the protocol fact it derives from, and carries a negative control — a mutation that provably breaks it. A claim is settled only after a discriminator agent has tried to break it.

LawStatement
M1every tool call receives exactly one answer — on refusal, failure, truncation, provider error, cancellation
M2a call whose arguments did not arrive complete is never executed
M3a failed tool is a result carrying isError, which the model reads and recovers from
M4a provider failure is an event, and M1 survives it
R1resident memory is O(window + context + one result), independent of run length
T1an exclusive tool runs alone; shared tools around it still run together
T4results are recorded in the order the assistant asked for them
replaythe same journal, replayed, produces the same context: fold(replay(log)) ≡ fold(log)

04A run, end to end

  1. the application asks the agent to do something
  2. the request goes through the host's prepareRequest — elide a stale result, switch the model for a turn — and out to the provider
  3. the model answers, and the run's journal grows: what the assistant said, what it asked for
  4. the host's approve is asked before each tool runs — it may wait for a human
  5. the tool runs with validated arguments, in the page, through the capability bridge
  6. the result is budgeted, journalled and fed back — and the loop repeats until the model is done, the turn limit is reached, or someone cancels

05Embedding it

// the host owns everything privileged: the model, the tools, the policy
import { runAgent, userMessage } from "miha/core";
import { openaiCompat } from "miha/llm";

const host = {
  callProvider: openaiCompat({ baseUrl: "https://api.minimax.io/v1", apiKey }),
  append: (entry) => save(entry),                    // the journal is yours to keep
  approve: async (call) => askTheHuman(call),         // the one permission seam
  prepareRequest: (request) => shape(request),       // optional, in flight
  summarize: async (collapsed) => askMyModel(collapsed),
};

const run = runAgent(config, host, { message: userMessage("read notes.txt") });
for await (const event of run) render(event);       // the live view
const outcome = await run.result();                  // completed | cancelled | failed | limitReached

That is the whole embedding surface. The budgets, the pairing, the pairing's survival and the journal's shape are the harness's laws — not your configuration.

07What it refuses to be

A harness is defined as much by what it will not carry. Each of these was considered, measured or prototyped — and refused, with the reason written down.

  • a model catalogue — the host owns the model
  • a permission engine — the host owns the policy; the core carries one async hook to it
  • a session store — the host owns it; the core appends by intent
  • progressive tool disclosure — the preregistered test found the hypothesis did not survive, and a moving tool list breaks the prompt cache
  • programmatic tool calling — a code tool over page-local actions is arbitrary script in the user's page
  • a graph runtime — the laws are checked by substitution on a pure function
  • telemetry — a journal that replays is worth more than a metric that aggregates
  • callable peer handles — a peer gets a task, never a handle on your tools
